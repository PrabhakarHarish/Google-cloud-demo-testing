1. THE CLOUD TESTING PART
================================================================================

Cloud Testing in this project focuses on validating cloud-native infrastructure,
Kubernetes architecture, container security configurations, and operational
resilience *before* and *during* deployment to Google Cloud Platform (GCP) / 
Google Kubernetes Engine (GKE).

Rather than testing typical application-level code loops, Cloud Testing tests the
governance, reliability, and security policies of the cloud deployment manifests.

Key Pillars of the Cloud Testing Implementation:

1. Architectural Completeness & Topology Verification:
   - Verifies that all 11 required microservices have their corresponding
     Kubernetes Deployment resources declared.
   - Ensures that every service intended to receive network traffic exposes a
     Kubernetes Service definition with correct port mappings, avoiding silent
     deployment omissions or broken inter-service communication.

2. Cloud Security Posture & Container Hardening:
   - Enforces the Principle of Least Privilege across all container pods based on
     cloud security standards (such as CIS Kubernetes Benchmarks).
   - Validates that pods enforce non-root execution (`runAsNonRoot: true`),
     preventing privilege escalation attacks inside the cluster.
   - Confirms `allowPrivilegeEscalation: false` to ensure containers cannot gain
     more privileges than their parent process.
   - Enforces immutable and pinned image versions (verifying that no service uses
     the mutable `:latest` tag, which can introduce unvetted code into production).

3. Quality of Service (QoS) & Resource Governance:
   - Cloud environments rely on multi-tenant cluster compute nodes. Without strict
     resource quotas, a single microservice with a memory leak can cause node
     instability ("noisy neighbor" effect).
   - Tests verify that every deployment specifies both `requests` and `limits` for
     CPU and memory. Requests guarantee scheduling thresholds in GKE, while limits
     prevent cluster resource starvation.

4. Self-Healing & Health Probes:
   - Checks that Kubernetes readiness and liveness probes are properly configured.
   - Readiness probes ensure GKE load balancers route user traffic only to pods
     that have completed startup routines.
   - Liveness probes enable GKE to automatically restart containers in case of
     deadlocks or unhandled background failures.

2. THE MICROSERVICES PART
================================================================================

The application core (located in `microservices-demo/`) represents Google Cloud's
"Online Boutique", a distributed, cloud-native e-commerce application composed of
11 loosely-coupled microservices written in different languages (polyglot):

1. `frontend` (Go):
   - Exposes an HTTP server serving HTML templates to client web browsers.
   - Translates incoming user HTTP actions into gRPC calls dispatched to
     internal backend microservices.

2. `cartservice` (C# / .NET):
   - Stores, retrieves, and clears shopping cart items per user session.
   - Interacts with Redis (or Google Cloud Memorystore) for data persistence.

3. `productcatalogservice` (Go):
   - Reads catalog information from an inventory store (`products.json`).
   - Supports listing products, retrieving specific products by ID, and text search.

4. `currencyservice` (Node.js):
   - Calculates currency exchange rates and converts money values between 30+
     global currencies (USD, EUR, JPY, GBP, CAD, etc.).

5. `paymentservice` (Node.js):
   - Handles credit card authentication and payment processing for checkouts.

6. `shippingservice` (Go):
   - Calculates shipping costs based on cart contents and destination address.
   - Creates and returns tracking numbers (`TRK-...`) upon order placement.

7. `recommendationservice` (Python):
   - Provides product recommendations ("You May Also Like") based on the items
     currently in the user's cart.

8. `checkoutservice` (Go):
   - Orchestrates the entire checkout transaction: aggregates items from
     `cartservice`, requests shipping fees from `shippingservice`, charges credit
     cards through `paymentservice`, generates confirmation orders, and calls
     `cartservice` to empty the cart.

9. `emailservice` (Python):
   - Sends HTML order confirmation emails upon successful checkout completion.

10. `adservice` (Java):
    - Evaluates product category tags to serve contextual advertisements.

11. `loadgenerator` (Python / Locust):
    - Generates synthetic, continuous background user traffic for demos and testing.

Microservices Communication Protocol:
- All inter-service communication uses high-performance **gRPC** over HTTP/2.
- Data structures and RPC method contracts are strictly defined using **Protocol
  Buffers v3 (protobuf)** in `demo.proto`.
- Microservices testing bypasses the frontend UI and executes RPC calls directly
  against these backend services.

3. THE UI AUTOMATION PART
================================================================================

The UI Automation suite (located in `testing_project/tests/e2e_playwright/` and
supported by `testing_project/pages/`) validates the web interface that end users
interact with.

Key Characteristics of the UI Automation Implementation:

1. Playwright Framework:
   - Uses Microsoft Playwright for Python (`playwright` & `pytest-playwright`).
   - Executes tests in headless or headed Chromium browser sessions.
   - Provides built-in auto-waiting for DOM elements, network idle states, and
     modern asynchronous event synchronization.

2. Page Object Model (POM) Design Pattern:
   - All HTML element selectors and low-level user actions (clicking, typing,
     selecting dropdowns) are isolated within dedicated Page Objects inside
     `testing_project/pages/`:
     * `base_page.py`: Common actions (navigation, currency picker, cart icon).
     * `home_page.py`: Product catalog grid, banner, item cards.
     * `product_page.py`: Quantity selector, product details, "Add to Cart".
     * `cart_page.py`: Item review, shipping address form, payment form, checkout.
     * `order_page.py`: Order confirmation message, Order ID, Tracking ID.
   - Keeps test scripts readable, modular, and maintainable when UI designs change.

3. Comprehensive User Flows:
   - Tests cover complete end-to-end shopping journeys: browsing catalog items,
     viewing product details, adding items to cart, modifying item counts,
     switching global currencies, entering billing/shipping data, submitting
     orders, and confirming receipt generation.

4. Responsive & Mobile UI Testing:
   - Includes viewport emulation to validate UI rendering and workflows on mobile
     dimensions (e.g., iPhone 375x667 viewport).

4. THE PROCESS WHERE CLOUD IS INVOLVED IN THIS PROJECT
================================================================================

Cloud technology is deeply integrated into every phase of this project, spanning
architecture, provisioning, deployment, communication, observability, and testing.

The Cloud Process Lifecycle:

1. Cloud Infrastructure as Code (IaC) & Resource Provisioning:
   - In `microservices-demo/terraform/`, Terraform code automates the creation
     of managed cloud resources on Google Cloud Platform (GCP):
     * Google Kubernetes Engine (GKE) clusters (nodes, node pools, VPC networking).
     * Google Cloud Memorystore (managed Redis instance used by `cartservice`).
     * Google Cloud IAM roles, service accounts, and least-privilege permissions.

2. Containerization & Cloud Artifact Storage:
   - Every microservice is packaged into an isolated OCI-compliant container image
     via multi-stage Dockerfiles.
   - Images are versioned and stored in Google Artifact Registry or Google
     Container Registry (GCR).

3. Cloud CI/CD Automation:
   - Defined in `cloudbuild.yaml` (Google Cloud Build) and `skaffold.yaml`.
   - Cloud Build automatically executes build steps, triggers test suites, and
     deploys updated container images directly into the Kubernetes cluster.
   - Skaffold provides continuous cloud-native deployment pipelines.

4. Cloud Orchestration on Google Kubernetes Engine (GKE):
   - Deployments, Services, and configurations are declared via YAML files in
     `microservices-demo/kubernetes-manifests/` and
     `microservices-demo/release/kubernetes-manifests.yaml`.
   - GKE manages pod scheduling, horizontal pod autoscaling (HPA), rolling zero-
     downtime deployments, and self-healing (restarting crashed containers).
   - Ingress and Cloud Load Balancing distribute external HTTP/HTTPS traffic from
     the internet to the `frontend` service pods.

5. Cloud Service Mesh & Security (Istio):
   - `microservices-demo/istio-manifests/` configures an Istio service mesh inside
     the GKE cluster.
   - Enforces mutual TLS (mTLS) for encrypted zero-trust inter-service traffic.
   - Manages intelligent routing, circuit breaking, and canary deployments.

6. Cloud Observability & Monitoring:
   - Microservices integrate with Google Cloud Operations Suite (formerly
     Stackdriver):
     * Google Cloud Logging: Centralized log aggregation across all containers.
     * Google Cloud Monitoring: Metrics, CPU/RAM usage, and alerts.
     * Google Cloud Trace / OpenTelemetry: Distributed tracing to trace gRPC
       requests as they hop across multiple microservices.

7. Cloud-Aware Testing Integration:
   - The test framework (`testing_project`) integrates with this cloud lifecycle
     in dual modes:
     * Pre-deployment Cloud Linting: Tests parse K8s YAML manifests to prevent
       misconfigured or insecure workloads from ever reaching the cloud.
     * Post-deployment Live Cloud Testing: By pointing `BOUTIQUE_BASE_URL` to a
       live GKE ingress endpoint, the exact same test suites validate the real,
       running cloud deployment.

5. UNDER 'testing_project/tests/': WHAT EACH FOLDER DOES EXACTLY
================================================================================

The `testing_project/tests/` directory is partitioned into three specialized
testing suites:
  1. `cloud_infra/`
  2. `microservices/`
  3. `e2e_playwright/`

Here is the exact, file-by-file and function-by-function explanation of each folder:

--------------------------------------------------------------------------------
5.1. `testing_project/tests/cloud_infra/` (Cloud Infrastructure Tests)
--------------------------------------------------------------------------------
Purpose:
Validates the structural correctness, container hardening, resource constraints,
and health-check policies of the Kubernetes deployment manifests located at
`microservices-demo/release/kubernetes-manifests.yaml`. It ensures cloud-readiness
prior to deployment.

Files and what they do:

1. `test_k8s_manifests.py`:
   - `test_all_11_microservices_deployments_exist`:
     Parses all YAML documents in the release manifest and verifies that all 11
     microservices (`frontend`, `cartservice`, `productcatalogservice`,
     `currencyservice`, `paymentservice`, `shippingservice`, `emailservice`,
     `checkoutservice`, `recommendationservice`, `adservice`, `loadgenerator`)
     have an active Kubernetes Deployment resource defined.
   - `test_all_microservices_expose_k8s_services`:
     Verifies that every core microservice exposes a Kubernetes `Service` object
     for internal cluster networking and discovery. Correctly excludes
     `loadgenerator` because it acts solely as a client traffic generator.
   - `test_container_image_tags_and_naming`:
     Inspects all container image strings. Ensures no service uses the mutable
     `:latest` tag (preventing untracked configuration drift) and verifies that
     images originate from official authorized repositories.

2. `test_health_probes.py`:
   - `test_frontend_health_probe_configuration`:
     Validates that the `frontend` Deployment defines both `readinessProbe` and
     `livenessProbe` using HTTP GET on port 8080 targeting the `/_healthz` endpoint.
   - `test_backend_microservices_probes_exist`:
     Checks that all 9 long-running backend microservices configure both
     `readinessProbe` and `livenessProbe` so GKE can monitor pod health and
     restart unresponsive services automatically.

3. `test_security_resilience.py`:
   - `test_least_privilege_security_context`:
     Verifies that every pod or container specifies `runAsNonRoot: true` and that
     `allowPrivilegeEscalation: false` is enforced in container security contexts,
     mitigating container breakout vulnerabilities.
   - `test_resource_requests_and_limits_defined`:
     Verifies that every deployment defines both `requests` and `limits` for both
     CPU and memory. Ensures Kubernetes schedulers can optimize pod placement and
     prevent resource starvation in the cluster.


--------------------------------------------------------------------------------
5.2. `testing_project/tests/microservices/` (Microservice Contract / gRPC Tests)
--------------------------------------------------------------------------------
Purpose:
Executes direct API contract tests against individual backend microservices via
gRPC protocol buffers, using `grpcio` and generated client stubs (`demo_pb2_grpc`).
These tests validate schema compliance, data correctness, and error handling
without needing any browser or web frontend.

Files and what they do:

1. `test_cart_service.py`:
   - `test_cart_add_and_retrieve`:
     Connects to `CartServiceStub`, adds a `CartItem` for a generated user ID via
     `AddItem()`, then invokes `GetCart()` to verify the item is present with the
     correct product ID and quantity.
   - `test_cart_empty_action`:
     Adds an item to a user's cart, invokes `EmptyCart()`, and asserts that a
     subsequent `GetCart()` returns zero items.

2. `test_catalog_service.py`:
   - `test_list_products`:
     Calls `ListProducts()` on `ProductCatalogServiceStub`, verifying that the
     catalog is non-empty and products have valid IDs, titles, and price schemas.
   - `test_get_product_by_id`:
     Retrieves a known product ID and verifies `GetProduct()` returns the exact
     matching product metadata.
   - `test_get_product_not_found`:
     Requests a nonexistent product ID and asserts that the gRPC server properly
     returns a `StatusCode.NOT_FOUND` error.
   - `test_search_products`:
     Sends a search query (`"sun"`) and verifies returned products match the text
     in either their title or description.

3. `test_currency_service.py`:
   - `test_get_supported_currencies`:
     Calls `GetSupportedCurrencies()` on `CurrencyServiceStub` and asserts that
     standard currencies (USD, EUR, CAD, JPY, GBP) are present in the list.
   - `test_currency_conversion`:
     Calls `Convert()` to convert an amount (e.g., 100 USD to EUR) and validates
     that the returned `Money` object contains EUR currency code and a positive value.

4. `test_payment_service.py`:
   - `test_charge_valid_credit_card`:
     Submits a valid mock credit card payment via `Charge()`, asserting that a
     valid transaction ID starting with `"TX-"` is returned.
   - `test_charge_invalid_credit_card`:
     Submits an invalid card number and asserts that the service correctly rejects
     the call with a `StatusCode.INVALID_ARGUMENT` error.

5. `test_recommendation_service.py`:
   - `test_list_recommendations`:
     Calls `ListRecommendations()` specifying a user ID and current product ID.
     Verifies recommendations are returned and that the current product is not
     recommended back to the user.

6. `test_shipping_service.py`:
   - `test_get_shipping_quote`:
     Calls `GetShippingQuote()` with an address and cart items, confirming that a
     valid, non-negative shipping fee is returned.
   - `test_ship_order`:
     Calls `ShipOrder()` with shipping address and items, verifying that an
     official tracking ID starting with `"TRK-"` is generated.


--------------------------------------------------------------------------------
5.3. `testing_project/tests/e2e_playwright/` (End-to-End Browser UI Tests)
--------------------------------------------------------------------------------
Purpose:
Drives authentic browser sessions via Playwright to simulate real shopper journeys
across the web frontend. Uses the Page Object Model (POM) pattern to assert UI
rendering, state synchronization, form processing, and end-to-end purchasing.

Files and what they do:

1. `test_home_page.py`:
   - `test_frontend_healthz_probe`:
     Sends an HTTP GET to `/_healthz` and asserts status 200 with an `"ok"` response.
   - `test_homepage_loads_successfully`:
     Navigates to the homepage and asserts that the title, store logo, and main
     headings are visible.
   - `test_hot_products_catalog_display`:
     Asserts that the product catalog grid loads items, each showing a title,
     image, and price with a valid currency symbol.
   - `test_initial_cart_badge`:
     Verifies that a new, unauthenticated browser session initializes with 0 items
     in the cart indicator badge.

2. `test_product_flow.py`:
   - `test_view_product_detail_page`:
     Clicks a product card on the homepage and verifies the product detail page
     loads the correct product name, price, description, and "Add to Cart" button.
   - `test_product_quantity_selector`:
     Selects an updated quantity (e.g., 3) from the dropdown and verifies the
     selector retains the chosen value.
   - `test_product_recommendations`:
     Verifies that the "You May Also Like" recommendation section is displayed
     at the bottom of the product page.

3. `test_cart_workflow.py`:
   - `test_add_product_to_cart`:
     Adds a product with quantity 2 to the cart, verifies redirect to `/cart`, and
     confirms the cart contains the item with the correct quantity.
   - `test_empty_cart_functionality`:
     Adds an item to the cart, clicks "Empty Cart", and asserts the cart becomes
     empty and shows the "Continue Shopping" button.

4. `test_checkout_workflow.py`:
   - `test_complete_checkout_user_journey`:
     Executes the full shopper workflow: browse home catalog -> select item ->
     add 2 units to cart -> verify cart summary -> fill in shipping address and
     payment credentials -> submit order -> assert order confirmation page
     displays a valid Order ID (`ORD-...`), Tracking ID (`TRK-...`), and total
     amount paid -> click "Continue Shopping" to return home.

5. `test_currency_switch.py`:
   - `test_currency_switch_to_eur`:
     Selects EUR from the currency dropdown and checks that prices display the
     Euro (€) symbol.
   - `test_currency_switch_to_jpy`:
     Selects JPY and verifies prices update to show the Japanese Yen (¥) symbol.
   - `test_currency_persists_on_product_page`:
     Selects a currency (e.g., EUR) on the homepage and navigates to a product
     page, confirming that the chosen currency persists across page navigation.

6. `test_responsive_ui.py`:
   - `test_mobile_viewport_layout`:
     Emulates a mobile viewport (375x667 pixels, iPhone size) to ensure header,
     navigation, product grid, and checkout buttons render responsively without
     clipping or layout breakage.

6. HOW THE APPLICATION IS DEPLOYED INTO GOOGLE CLOUD AND TESTED THERE
================================================================================

This section details the concrete steps for deploying the entire Online Boutique
microservices stack to Google Cloud Platform (GCP) and how quality assurance and
testing are conducted directly against the live cloud deployment.

--------------------------------------------------------------------------------
6.1. Deployment Process into Google Cloud (GKE)
--------------------------------------------------------------------------------

The deployment targets Google Kubernetes Engine (GKE), Google Cloud's managed
Kubernetes service.

Step 1: GCP Project Setup & API Initialization
  - Create or select a Google Cloud Project:
      gcloud config set project <PROJECT_ID>
  - Enable the required Google Cloud APIs:
      gcloud services enable container.googleapis.com \
                             artifactregistry.googleapis.com \
                             cloudbuild.googleapis.com

Step 2: Provision the GKE Cluster
  - Create an Autopilot or Standard GKE cluster:
      gcloud container clusters create-auto online-boutique \
        --project=<PROJECT_ID> \
        --region=us-central1
  - Connect your local shell to the newly created GKE cluster:
      gcloud container clusters get-credentials online-boutique \
        --region=us-central1 \
        --project=<PROJECT_ID>

Step 3: Deploy the Microservices Manifests
  - Deploy the complete 11-microservice stack using the pre-built, production-ready
    release manifest:
      kubectl apply -f microservices-demo/release/kubernetes-manifests.yaml
  - (Optional IaC alternative: Deploy via Terraform scripts in
    `microservices-demo/terraform/` or Helm charts in `microservices-demo/helm-chart/`).

Step 4: Monitor Pod Rollout & Acquire Public Ingress IP
  - Wait for all 11 microservice pods and the Redis store to reach the 'Running' state:
      kubectl get pods -w
  - Retrieve the external LoadBalancer IP assigned to the `frontend-external` service:
      kubectl get service frontend-external
    The output displays the public IP in the EXTERNAL-IP column:
      NAME                TYPE           CLUSTER-IP      EXTERNAL-IP     PORT(S)
      frontend-external   LoadBalancer   10.128.15.240   34.123.45.67    80:31234/TCP

At this point, the application is live and accessible globally at `http://34.123.45.67`.


--------------------------------------------------------------------------------
6.2. How the Application is Tested in Google Cloud
--------------------------------------------------------------------------------

Once deployed to GKE, testing shifts from static pre-commit linting to live cloud
environment validation across multiple layers:

1. Dynamic Dual-Mode Testing via Environment Variables:
   - The test framework (`testing_project`) has a built-in live cluster detection
     mechanism in `testing_project/conftest.py`.
   - By setting the `BOUTIQUE_BASE_URL` environment variable to point to the GKE
     public IP:
       export BOUTIQUE_BASE_URL="http://34.123.45.67"
   - When `pytest` is invoked, `conftest.py` sends an HTTP probe to:
       http://34.123.45.67/_healthz
   - Detecting an active, healthy cluster, `conftest.py` automatically bypasses
     all local mock servers (no local Flask, no local mock gRPC). All test fixtures
     now directly communicate over the internet with the live Google Cloud cluster.

2. Executing End-to-End Browser UI Automation Against GCP:
   - Run the Playwright suite targeting the cloud deployment:
       .venv/bin/python -m pytest testing_project/tests/e2e_playwright/
   - Playwright launches Chromium browsers and navigates directly to the GKE
     LoadBalancer IP.
   - It executes real shopping flows: browsing items, selecting currency, adding
     items to the cloud-backed Redis cart, filling checkout info, and verifying
     that real order transactions complete on the cloud-hosted frontend.

3. Testing Internal Backend Microservices via Secure gRPC Tunneling:
   - For security, internal gRPC microservices (such as `cartservice`,
     `productcatalogservice`, `currencyservice`, and `paymentservice`) are not
     exposed directly to the public internet.
   - To execute microservice contract tests against the live pods in GKE, port-
     forwarding creates an encrypted local tunnel into the cluster:
       kubectl port-forward svc/frontend 8080:8080 &
       kubectl port-forward svc/cartservice 7070:7070 &
       kubectl port-forward svc/productcatalogservice 3550:3550 &
   - Set the gRPC endpoint configuration:
       export BOUTIQUE_GRPC_HOST="127.0.0.1"
       export BOUTIQUE_GRPC_PORT="50051"
   - Run the microservices suite:
       .venv/bin/python -m pytest testing_project/tests/microservices/
   - This validates that live containerized services in GKE adhere strictly to
     the gRPC protobuf contracts.

4. In-Cluster Continuous Traffic & Load Testing:
   - The deployed `loadgenerator` pod runs natively inside GKE as a continuous
     Locust workload.
   - It generates synthetic, concurrent user traffic hitting the frontend and
     backend services 24/7, testing throughput, latency, and auto-scaling.

5. Cloud-Native Reliability, Probes & Observability:
   - Kubernetes Runtime Probes: GKE continuously polls the `readinessProbe` and
     `livenessProbe` on each pod. If any service fails or deadlocks under load,
     GKE automatically evicts traffic or restarts the container.
   - Google Cloud Operations Suite (Cloud Logging & Cloud Monitoring):
     * In the GCP Console, Cloud Logging aggregates all standard output and error
       streams from all 11 microservices in real time.
     * Cloud Monitoring displays CPU, memory saturation, and HTTP response codes.
     * Google Cloud Trace records distributed traces across gRPC hops, measuring
       latency from the `frontend` to `checkoutservice`, `paymentservice`, and
       `shippingservice`.
